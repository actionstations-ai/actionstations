# Spec 0451: Health informatics and clinical IT, and the clinical systems toolkit

Issue: #684 (epic) · Milestone: Backlog · Status: Draft · Depends on: #648 (toolkits, spec 0448) · Research: [docs/research/domains/health_informatics.md](../research/domains/health_informatics.md)

## Summary

Hospitals must exercise their emergency plans every year, and HIPAA expects contingency plans to be tested, yet few have rehearsed what happens when the electronic health record goes dark. This epic adds a `health_informatics` domain, a variant of the existing `healthcare` organization seen from the clinical IT desk (CIO, CMIO, CNIO, EHR analysts, interface analysts, health information management, clinical engineering), and the **clinical systems toolkit**: EHR screens in normal, degraded and read-only states, downtime reports and paper forms, an interface status dashboard with HL7 and FHIR message views, a results backlog and a reconciliation worklist. Players work an unplanned downtime, a ransomware recovery or an identity overlay on synthetic patients, make structured decisions (declare downtime, choose restore order, release a result, notify), and are scored on time to downtime procedures, safe-care measures, reconciliation and notification clocks. Because it is a toolkit, nursing (spec 0452), pharmacy (spec 0463) and any domain with a records system can use the same screens and reports.

## Requirements

### User stories

- As a CMIO, I want a 24-hour unplanned EHR downtime where my clinical leaders decide which workflows stay on paper and which results to trust when systems return.
- As a hospital emergency manager, I want the annual second exercise (42 CFR 482.15(d)(2)(ii)(C), Joint Commission EM.16.01.01) to be a facilitator-led tabletop with a clinically relevant scenario, produced with the problem statements and after-action report the rules describe.
- As an interface analyst, I want to see an error queue and decide what to replay, discard or hold, then find out what that did to the patient.
- As a CNIO, I want the same downtime scenario to produce the paper forms my units will actually print, so the nursing side can play it (spec 0452).
- As a privacy officer, I want a snooping incident that runs the four-factor risk assessment and the notification clocks in real time.
- As a health informatics instructor, I want a two-hour lab on a synthetic hospital with no access to real systems.

### Functional requirements

**Domain**

- **FR-1 Health informatics domain.** A `health_informatics` domain profile that **extends** the `healthcare` profile (roles, outside parties, media, phrasing inherited, nothing duplicated) with the clinical IT roles in the research dossier (section 2), variants for a hospital IT and informatics team, an HIM and clinical engineering team, and a university informatics program lab, and the aliases in the dossier (section 1). It shares the hospital incident command of the `healthcare` profile; a project can run both together.
- **FR-2 Threat families and arcs.** Clinical forms of the shared **service degradation** family (spec 0449 FR-2): EHR unavailable (planned or unplanned), interface failure or message loss, identity overlay, wrong clinical decision support, device network loss, telehealth outage, third-party failure; each with the phase arc in the dossier (section 9) and an inject purpose mix, using extensible families (spec 0448 FR-15). Existing cyber, insider and third-party families are reused, with clinical-systems variants.

**Clinical systems toolkit: products**

- **FR-3 Products as templates.** Exact, legible templates for the products in dossier section 4: EHR screens (patient list, results review, MAR, order entry) in normal, degraded and read-only states; downtime census and bed board report; downtime paper forms (order sheet, requisitions, nursing flowsheet, registration form); HL7 v2 message view and FHIR resource view; patient identity worklist; CDS alert log and override report; breach risk assessment worksheet; recovery readiness checklist. The existing healthcare templates (`ehr_downtime_notice`, `hl7_interface_monitor`, `downtime_med_admin_form`, `patient_portal_banner`, `breach_notification_letter`, `hics_251_status`, `device_safety_communication`) are reused, extended where needed, and not rebuilt.
- **FR-4 Synthetic patients.** All patient data is synthetic: names, record numbers and dates are generated by an app-side generator (fictional by construction, project naming rule), with age, diagnoses, medications, allergies and recent results consistent with one another. Real record data is never required or imported (see FR-9 for the reference datasets used only for plausible value ranges).
- **FR-5 Format rules.** Lint and generator knowledge: HL7 v2 segment and field syntax for the message types shown (ADT, ORM, ORU) with decoded fields matching the raw text, FHIR resource shape checks against the CC0 specification, record-number formats from the scenario's facts, and conventions (downtime forms carry the as-of time and the printing system; read-only viewers show "as of" stamps; critical results are phoned, not mailed). Packs do not bundle the HL7 v2 standard text.

**Clinical systems toolkit: figures**

- **FR-6 Figures.** Figure kinds (spec 0448 FR-4) for: interface status dashboard (feeds, direction, status, queue depth, last message), message queue time series, unit status board (green/amber/red, staff on downtime), results backlog (count by department and age, oldest item), reconciliation progress (done versus remaining by unit), downtime timeline (events against the clock). Each has the text summary and data table of spec 0448 FR-5. None are AI images.

**Clinical systems toolkit: data and simulation**

- **FR-7 Simulated downtime.** For a fictional hospital, parameters (size, units, which systems fail, start time, duration, whether data is lost) produce consistent case data (spec 0448 FR-10): census by unit, order and result volumes per hour, queue growth and drain, backlog size at recovery, a set of seeded discrepancies (a duplicate record, a result attached to the wrong patient, an order sent twice), all labeled simulated. Volumes per hour are scaled by bed count, with the multiplier shown to the facilitator.
- **FR-8 Event replay as narrative.** Past incidents (dossier section 8) are offered as **dated scenario seeds** with the facts attributed, not as data feeds; the generator is told they are history. No real organization's name is used for the exercising organization (project naming rule).
- **FR-9 Reference value ranges.** Plausible lab and vital-sign ranges and message shapes are taken from the open synthetic generator output and the FHIR specification, bundled as small reference tables in the toolkit (Synthea is Apache 2.0, FHIR is CC0, per dossier section 6). The MIMIC-IV demo (ODbL) is not bundled; if used for value ranges, its attribution and share-alike terms are met in the pack notices.

**Exercise play**

- **FR-10 Clinical IT decisions.** Structured decisions (spec 0448 FR-14): "Declare downtime" (systems, planned/unplanned, expected duration, who is told), "Set restore order" (a ranked list of systems and interfaces with the reason), "Hold, replay or discard" a message class, "Release a result" or "Hold results until validated", "Open a duplicate or overlay merge", "Isolate devices", "Notify" (who, what, when) and "Return to normal". Available to players in live play and to the facilitator in Facilitate; they enter the session log and feed FR-11.
- **FR-11 Consequence engine.** Decisions change case data in a simple, explainable way: a restore order that brings the EHR up before the lab interface increases the results backlog and the chance of results attached to the wrong patient; discarding a message class records the orders at risk; holding results delays care but lowers wrong-patient risk. The facilitator sees the rule that fired and can override it. The rules are a small table in the toolkit, not a model of real systems.
- **FR-12 Reconciliation play.** After recovery, units back-enter from paper; a progress figure and a discrepancy list drive injects ("two patients share a record number"), and the exercise ends when the facilitator closes reconciliation.

**Evaluation**

- **FR-13 Metrics.** Using the built-in metrics of spec 0448 FR-12 plus clinical systems measures: time from declaration to all units on downtime procedures; orders and results lost, delayed or duplicated; critical results communicated within the scenario's target; late or missed medication doses (from the nursing toolkit when on, spec 0452); reconciliation time and percent complete; duplicate records created; notification clocks met (spec 0426); restore order scored against a clinician-defined priority list; diversion decisions. Each shows its inputs.
- **FR-14 Core capabilities.** EEGs for Operational Communications, Operational Coordination, Situational Assessment, Public Information and Warning, Cybersecurity, Logistics and Supply Chain Management and Health and Social Services, with critical tasks specific to clinical IT; the after-action report groups findings under the Joint Commission six critical areas (communications, staffing, patient care and clinical support, safety and security, resources and assets, utilities) for hospital exercises.
- **FR-15 Compliance documentation.** The after-action report and improvement plan are produced in the shape the CMS rule and the Joint Commission standard describe (exercise type, scenario basis, analysis of response, revisions to the plan, committee review), and a one-page exercise record states which annual exercise it satisfies **as an aid, without claiming compliance** (the hospital's compliance office decides).

**Knowledge and reuse**

- **FR-16 Document library.** A public-domain library pack: HHS 405(d) HICP documents, ASPR TRACIE EHR downtime and cybersecurity resources, ONC SAFER Guides (Contingency Planning), CMS State Operations Manual Appendix Z, CISA healthcare tabletop packages, HHS OCR ransomware fact sheet, and the regulation text of 42 CFR 482.15 and 45 CFR 164.308(a)(7) and 164.400 through 164.414 as generated extracts (verify each license and URL when building the pack; builds on the healthcare pack's verified list). Joint Commission, HL7 v2 and vendor documents are named, not bundled.
- **FR-17 Examples.** (1) A 24-hour unplanned EHR downtime for a fictional community hospital: declaration, paper workflows, restore order and reconciliation. (2) Ransomware recovery for a fictional health system with an interface engine failure and a results backlog. (3) A snooping incident and breach risk assessment with notification clocks, run as a 90-minute informatics-program lab.
- **FR-18 Reuse by other domains.** Suggested toolkits added to `healthcare` (clinical systems, cyber, regulatory clocks), `public_health` (clinical systems for lab reporting feeds) and the nursing and pharmacy profiles (specs 0452, 0463); EMS and fire, behavioral health and research labs when those fields are built.

### Non-functional requirements

- **NFR-1 Cost:** only free public sources; no accounts or keys; reference datasets are bundled or generated locally.
- **NFR-2 Privacy:** no real patient data enters the app. The generator, reference tables and templates are synthetic; documents imported by the user that look like they contain patient identifiers trigger a warning and redaction offer (spec 0433). Nothing about the user's systems or plans is sent anywhere by the toolkit.
- **NFR-3 Accessibility:** every figure has a text summary and data table; status colors (green, amber, red) always carry words and icons, not color alone; paper-form templates export as accessible PDF.
- **NFR-4 Accuracy:** formats verified against the published specifications and regulations cited in the dossier; every regulatory statement in templates carries a retrieval date; a review of templates, restore-order rules and examples by a CMIO or CNIO and a hospital emergency manager before release (owner to arrange). Exercise products are marked as exercises.
- **NFR-5 Size:** simulated downtime data is generated, not stored in bulk; a scenario's case data stays under the default limit of spec 0448 NFR-4.

### Out of scope

- Connecting to any real EHR, interface engine or device; no HL7 or FHIR network traffic.
- Medical advice: clinical content in injects is plausible, marked as exercise content, and reviewed, but not a clinical reference.
- Legal advice or a statement of regulatory compliance.
- Modeling the full behavior of vendor products; the consequence engine is a small rules table.

## Design

- **Domain:** `packs/domains/health_informatics.json` (bundled pack) with variants as role sets, extending `healthcare` through the profile inheritance of ADR-0014.
- **Toolkit:** `packs/toolkits/clinical_systems/` (toolkit JSON, templates, knowledge fragments, lint rule configuration, reference tables, consequence rules table, decision forms).
- **Figures:** `src/main/render/figures/clinical/` (interface dashboard, queue series, unit status board, results backlog, reconciliation progress, downtime timeline); generic kinds from spec 0448 are used where they suffice.
- **Synthetic generator:** `src/main/toolkits/clinical/synthetic.ts` (patients, orders, results with consistent values, seeded discrepancies) and `src/main/toolkits/clinical/downtime.ts` (volume, queue and backlog model, consequence rules). Deterministic given a seed, so exercises replay.
- **Lint:** rule kinds `hl7v2_syntax` and `fhir_shape` added to the fixed lint set of spec 0448 FR-1.
- **Compliance record:** an after-action template pair in the HSEEP document set (spec 0420) with the hospital fields.

## Security and privacy

As spec 0448 plus: no real patient data; synthetic generator output only; imported documents scanned for identifiers before use in prompts to cloud providers (spec 0433); packs contain no vendor credentials, hostnames or logos.

## Testing

Golden images for each figure from fixed fixtures; lint tests for HL7 v2 and FHIR samples (valid, invalid); generator tests (deterministic output, consistency of values, seeded discrepancies appear); downtime model tests on worked examples (queue growth equals arrival minus drain); consequence rule tests for each rule; metric tests for time to downtime procedures and reconciliation on worked timelines; example projects generated end to end with the local model before release.

## Open questions

- **Practitioner review.** Recommendation: a CMIO or CNIO and a hospital emergency manager who has run a downtime exercise review the templates, restore-order rules and examples.
- **Epic catalog correction.** The fields catalog summarizes the CMS rule as a full-scale exercise "every two years"; the verified text is annual (dossier section 5). Recommendation: correct the catalog when the coordinator merges.
- **Exercise record wording.** Whether to state which Joint Commission exercise a tabletop satisfies. Recommendation: include the line as an aid with a visible disclaimer and let the hospital's compliance office edit it.
- **MIMIC-IV demo.** ODbL share-alike may affect a bundled pack. Recommendation: do not bundle; use Synthea and the FHIR specification only.
