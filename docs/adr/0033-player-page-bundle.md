# ADR-0033: The player page is its own small bundle

Date: 2026-10-29 · Status: Accepted · Issue: #411 · Spec: [0411](../specs/0411-player-page.md) · Related: ADR-0027 (protocol), ADR-0017 (windowed lists), #407, #412–#416, #422

## Context

Players open the live-play page on their own phones, tablets and laptops over a room's Wi-Fi or a relay (#418). The page must load in a couple of seconds on a mid-range phone, make no request to any origin but the one that served it, meet WCAG 2.2 AA, reconnect by itself after the device sleeps, and be the one surface every later live feature (injects, messages, votes, hot wash, evaluator forms, surveys) plugs into. The Electron renderer is a desktop app: TanStack Query, Zustand, Radix, a router and the full font set, several megabytes that a phone on guest Wi-Fi should not download. The LAN server (#407) and the relay (#408) also need a fixed list of files to serve, with hashes.

## Decision

- **A second Vite bundle**, `src/player/` → `out/player/` (`vite.player.config.ts`, `pnpm build:player`), packaged as `app-resources/player/`. React and TypeScript as the rest of the app, but no router, no query cache, no Zustand and no Radix: a screen state machine (join → room → ended, with the terminal screens beside it), a 40-line observable store and the protocol library from `src/shared/live/`. First load is about 130 KB gzipped against a 250 KB budget that `scripts/check-player-bundle.mjs` enforces; the pure-JavaScript crypto fallback loads lazily only in a non-secure context.
- **Shared tokens, no shared components.** `styles/player.css` imports the renderer's `tokens.css` so colors, type and spacing are the same system in light and dark; every component is the page's own. No fonts are bundled: the token stacks fall back to the system font, so the page makes no font request.
- **The build writes `manifest.json`** (served path → file, content type, size, gzipped size, sha256). Servers build their fixed route map from it and never touch the filesystem with request input; the packaged smoke check and the size budget read it too.
- **CSP without `unsafe-inline`.** The page's own `<meta>` locks scripts, styles, images, media and fonts to `'self'`; the one inline script (the theme bootstrap that prevents a light flash) is hashed into `script-src` at build time. Connections are governed by the server's CSP header, which names the exact `ws(s)://host:port`; a page cannot know its host and a scheme-only source would be looser.
- **Transports behind the client interface.** The page runs the same `LiveClient` as the app, over a browser WebSocket transport first and the SSE + POST fallback when a socket cannot open (Safari and a certificate it has not trusted, #407). The connection contract lives in `src/shared/live/connect-url.ts` so every server parses what the page sends: the client id in the query, the join and resume tokens in the WebSocket subprotocol list (`as-live.v1, j.<token>, r.<token>`; the server echoes the version only) or in the `X-AS-Join` and `X-AS-Resume` headers of the stream and send requests. Tokens never travel in a URL, because query strings end up in request logs and proxies, and a server refuses a request that puts one there. The fallback reads the event stream with `fetch` rather than `EventSource` for that reason.
- **One `LiveClient` per connection, one identity per session.** A dropped connection builds a new client over a new transport with the same keys, client id, resume token, `seq` and last catch-up index (`sessionStorage`), then re-joins with `resume: true` and asks for catch-up after the last index. Backoff is 0.5 s to 30 s with jitter; visibility, online, pageshow and focus events retry at once or, on a live connection, send a catch-up request as a liveness probe. A root received in a rotation is kept in the same tab's `sessionStorage` so a reload after another device was removed still works.
- **Lobby, then seat.** The page's first `join` asks for nothing; the controller answers a `welcome` without a `role` that carries the seats (`WelcomePayload.seats`: name, team, kind, capacity, taken) and the attribution level, which is what the join screen needs. The second `join` names the seat. A device the controller already seated gets its seat back on any later `join`, so reloads and reconnects need no local memory of the seat.
- **Items are kept, not filtered, on arrival.** The page keeps every frame it can open and decides at render time what is inbox (injects to its role, team or device) and what is feed (items to all, notices, clock changes, announcements), so a reseat rebuilds the inbox from what the page already holds and nothing is fetched twice.
- **A development harness instead of the app.** `src/player/harness/` serves the built bundle on loopback the way the LAN server will (route map from the manifest, CSP header, `/s/<id>`, WebSocket and SSE + POST bridges into `MemoryServer`) with a scripted controller. Unit tests, Playwright tests and `pnpm dev:player` run against it; it never ships.

## Consequences

- Live features add a screen and a few store fields; they do not add a router, a data layer or a second copy of the protocol. `features/` folders per sub-spec plug into `items.ts` (what a frame becomes) and `MoreScreen` (where a tab lives).
- The page shares no React component with the renderer, so a renderer change cannot break a phone and the two can be styled apart; shared visual language comes only from the tokens.
- The spec's `base: './'` could not be used: the page is served at `/s/<sessionId>`, so asset URLs are absolute (`/assets/...`), and a server must serve `/assets/*` at its root.
- The two-step join adds one round trip per device before the seat list appears (a few milliseconds on a LAN). The controller side (#418's `session.ts`) must answer a lobby `join` with the seats and re-seat a known device on any `join`.
- Items sort by exercise time, as the spec asks; with the clock paused at 0:00 a notice sorts below timed injects. Facilitators normally start the clock before releasing anything.
- No service worker in 0.6.0: a closed tab holds nothing, and a page served by the relay always runs the version the relay serves.
