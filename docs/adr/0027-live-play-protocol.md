# ADR-0027: Live play protocol and end-to-end encryption

Date: 2026-10-28 · Status: Accepted · Issue: #406 (revised after the security review of PR #449) · Spec: [0406](../specs/0406-live-protocol.md) · Related: #407–#418

## Context

Live play (#418) puts injects, messages, votes, hot wash items, surveys and evaluator observations on participants' own devices during an exercise. Three kinds of server can sit between the facilitator's app and those devices: the laptop itself on the room's Wi-Fi (#407), the project's relay on Cloudflare's free plan (#408), or a server an organization runs (#409). Exercise content is often sensitive (an organization's plans, its gaps, what its staff did under pressure), and the project rules say no server may learn it (CONTRIBUTING.md, Project rules 3). The features must be written once and behave the same over every connection, and the relay must cost nothing (Project rules 1).

Evaluation material has a stricter boundary than the rest. Expected actions, evaluator assignments and observations, controller notes and SimCell drafts must not be readable from a player's phone, including by a player who edits the page in their browser. The owner decided this is a key boundary from the first release, not a UI filter.

## Decision

One versioned protocol in `src/shared/live/` (no Node or DOM imports; it runs in Electron main, Vitest and the player page), with the servers importing only the schemas and limits.

- **Envelope.** One JSON text frame, exactly `v, session, seq, from, to, type, ts, payload, sig?`; unknown fields fail validation; forward compatibility is through `v`. Zod schemas for the envelope and every payload are the source of truth.
- **Two session keys.** A 256-bit **staff root** `K_t` is generated per session; the **players root** `K_p` is derived from it with HKDF, so a staff link can read everything and a players link cannot derive the staff key. Each root derives its own AES-256-GCM key. `Ciphertext.k` names the key and epoch (`s<epoch>` players, `t<epoch>` staff). `KEY_BY_TYPE` fixes which key each type travels under; `eval.assign` and `eval.observation` are staff-only, an `inject.release` carrying `expectedAction` is sealed with the staff key by itself, and a frame under the wrong key is dropped (`WRONG_KEY`). A player's device drops staff frames as `STAFF_ONLY`, which is expected and not an error.
- **Sealing.** AES-256-GCM with a random 96-bit nonce and the envelope header as additional authenticated data (`JSON.stringify([v, session, seq, from, to, type, ts])`). A server holds no key, so it cannot produce or alter a payload a client accepts, and a stored frame edited at rest fails exactly like a live one because catch-up goes through the same `open()`.
- **Frames to the controller are for the controller alone.** Every frame whose `to` is `controller` (join, receipts, votes, answers, hot wash items, observations) is sealed with a per-message key: ECDH between a fresh ephemeral key, sent in the ciphertext, and the controller's ECDH public key carried in the invite. Every device holds the players key, so a shared key could never keep one player's answers from another; the per-message key does, whatever a server hands out. The server also filters catch-up by `to` and never returns a client's own frames, but nothing depends on that.
- **Claims are proven, not declared.** A device that joins as a staff kind proves it holds the current staff root with `join.staffProof`, an HKDF of that root bound to its client id and ECDH key; the controller grants staff material (the staff root at a rotation, assignments) only to proven staff. A client id is bound to the device that first used it by a resume token whose hash the server keeps; a connection with a known id and another token is refused. Participants are told nothing about other clients.
- **Authority.** Controller types carry an ECDSA P-256 signature over header and ciphertext. The public key travels in the invite, never from a server, so a server cannot substitute a controller. Co-controllers (#440) are admitted by a host-signed roster with scopes, checked client-side.
- **Invite links.** `<base>/s/<sessionId>#<fragment>`: the fragment carries a layout byte (`0x01` players link, `0x02` staff link), epoch, root, the controller signing public key and the controller ECDH public key (165 bytes, 220 characters), and never reaches a server. Two links per session; the staff link is never shown on the main screen. The join token is derived from `K_p` and presented on connect; the server stores only its SHA-256.
- **Replay and ordering.** `seq` is strictly increasing per sender; a `ReplayGuard` on every receiver drops duplicates and lower values; the session id is in the AAD so frames do not cross sessions. Nonces are random, not derived from `seq`, so a lost counter cannot break confidentiality.
- **Rotation.** The controller makes a new staff root for epoch + 1 and sends each kept client the root it is entitled to (by its `join.kind`), wrapped under a pairwise ECDH key from the client's `join.ecdhPub`. Kicked clients and old links fail at the server (join token) and at the client (unknown epoch).
- **Blobs.** Media is one AES-GCM message under a per-blob key derived from the epoch root, chunked for transport only; the receiver buffers at most the size the reference announced. Chunk sizes are chosen so a chunk frame fits under the connection's envelope cap (45 KiB on the relay, 180 KiB elsewhere), so one size rule covers every frame. Caps per connection kind and per uploader are in `LIMITS`.
- **Crypto providers.** WebCrypto where `crypto.subtle` exists; otherwise a pure-JavaScript provider on `@noble/ciphers`, `@noble/curves` and `@noble/hashes` (MIT, no dependencies of their own, loaded lazily) for the player page over plain HTTP on a trusted LAN. Both pass the same vector file and open what the other sealed. Only algorithms every supported browser and Node 22 ship: AES-GCM, ECDSA P-256, ECDH P-256, HKDF-SHA-256, SHA-256.
- **Nothing from a server is trusted.** Hello caps are clamped to the protocol's limits, the `seq` hint is bounded, server frames or nested batches inside a catch-up batch are dropped, and live frames wait for an in-flight catch-up so stored frames are not mistaken for replays.
- **Client library and test server.** `LiveClient` is the connection-agnostic state machine (hello, join, welcome, catch-up, rekey, blobs, drop counts) over a four-method `Transport`. `MemoryServer` implements the server contract in process (size cap, parse, `from` check, `seq`, controller-only types, store, route, catch-up, blobs, presence) so features and servers test end to end with no sockets.

## Consequences

- Any server operator, including the project and Cloudflare, sees session ids, client ids, sizes, timing, addresses and opaque destinations, and nothing else. The relay stores ciphertext rows and never needs to read a payload.
- Staff material cannot be read from a player's device, whatever that device's page does, and no device can read what another device sent to the controller. Between player roles the boundary for controller-to-player frames is still a UI filter in v1 (everyone shares the players key); per-role keys are reserved (`k = "r:<roleId>:<epoch>"`) for a later version.
- A holder of a leaked players link can read what the players key seals until the facilitator rotates, and nothing else; the spec's threat model says so and the connection screen will.
- Co-controllers (#440) cannot read frames sealed to the host; #440 decides whether the host shares its ECDH key or the roster carries a second one.
- Each device sends one ECDH key agreement per frame to the controller (about a millisecond on a phone); controller-to-device traffic is unchanged.
- Two links to manage per session: facilitators hand the staff link to evaluators and SimCell helpers separately. Rotation produces two new links.
- The protocol library adds three MIT dependencies totalling about 3 MB unpacked, loaded only in non-secure contexts; secure contexts and the Electron app use WebCrypto and never load them.
- Ed25519 would be smaller and faster but is not yet reliable in every supported browser; moving to it is a `v: 2` change.
- An `eval.assign` of 120 tasks fits the relay's 64 KiB frame only with short tasks and citations; #416 trims with `estimateFrameBytes` or splits an assignment.
